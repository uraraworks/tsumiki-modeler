# つみきモデラー 作業計画

作成日: 2026-09-06

## このリポジトリの位置づけ

企画メモ 14 節「実装ステップ」の 1〜5 を、GitHub Pages で動くブラウザツールとして
段階的に実装する。いろはペイント／おとはピアノに続くシリーズ第3弾。

## 技術構成（プロトタイプ段階）

| 項目 | 選択 | 理由 |
|---|---|---|
| 実装 | 素の HTML + ES Modules（ビルド不要） | GitHub Pages に置くだけで動く。試行のサイクルが最短 |
| Three.js | CDN (jsdelivr) を importmap で読む | npm/Vite 導入は必要になってから |
| 言語 | JavaScript（TS は後回し） | プロトタイプ段階で型定義に時間を使わない |

> いろはペイントは Vite + TS だが、こちらは「動きを見ながら進める」段階なので
> あえてビルド無しから始める。規模が育ったら Vite へ移行する（src/ をモジュール分割しておく）。

## 最初から守る設計ルール（企画メモ 15 節）

MCP 対応を後から無料で足せるようにするため、以下 2 点はプロトタイプ第一版から守る。

1. **単一 JSON ドキュメントが唯一の真実**
   - `ModelDoc`（parts / bones / textures …）が状態のすべて
   - Three.js のシーンはそこからの派生物。逆方向に状態を持たない
   - パーツは安定 ID ＋ 意味のある名前（`arm_l` など）を持つ
   - 座標・寸法は整数グリッド単位
2. **すべての編集はコマンド経由**
   - `add_box` / `set_transform` / `delete_part` …
   - Undo/Redo はコマンド履歴で実現し、そのまま MCP の API になる

## 決めたこと・ペンディング

- 拡大は必ず整数倍。端数はレターボックス（黒帯）で埋める（企画メモ 3 節の絶対ルール）
- 1グリッドあたりの解像度は `doc.texelsPerUnit`（既定4）。箱は Minecraft / Blockbench 型の box UV、円柱は上下円＋側面帯へ自動展開する
- `doc.palette` は最大36色、テクスチャの `.` はパーツ色へフォールバックする。既存JSONは読込時に既定値を補い、textureなしの単色表示を維持する
- テクスチャは NearestFilter、mipmap 無効、SRGB。寸法変更時は左上基準で転写し、範囲外の着色ピクセル消失をステータス通知する
- ペイントはRaycasterのUVをアトラス座標へ変換し、同一パーツ・同一面内だけ直線補間する。1ストロークを`paintPixels`コマンド1件として確定する
- ボーンは親からの相対位置・回転を持つObject3D階層とし、パーツは1ボーンへ剛体割り当てする。パーツ座標は従来どおりモデル原点基準で、全ボーン回転0度をバインドポーズとする
- アニメーションはクリップ配列で保存し、現段階のUIは先頭クリップだけを扱う。フレーム移動の姿勢適用は履歴外、キー・fps・長さの編集はコマンド履歴へ積み、回転補間にはQuaternionのslerpを使う
- アウトラインは逆押し出しで開始。深度＋法線のエッジ検出は後で置き換え
- 公開先リポジトリ名は `tsumiki-modeler`（企画メモ 17 節）— まだ作成していない

## メッシュ統合をいつ判断するか

現在はパーツを組み合わせる方式なので、接合部は**めり込んだまま**（内側の面が残る）。
不透明・トゥーン・384x216 では実害が無いが、**Phase 5 でボーンを入れて関節を曲げると、
接合部が割れて中身が見える**可能性がある。

一般的なキャラ制作は「1つの繋がったメッシュを押し出し・分割で成形する」方式で、
企画メモ12節も「メッシュは繋がっている方が、Blockbench 的なパーツ分離よりずっと良い」としている。

ただし**先回りしてデータモデルを作り替えない**。ModelDoc は今「パーツの配列」だが、
押し出しを入れると「頂点と面の配列」が必要になり、改造が大きい。

**判断の順序（決定）**
1. まず現状のパーツ分離のまま Phase 5（ボーン + 剛体スキニング）を通す
2. 実際に関節を曲げて、384x216 でどれだけ割れが目立つかを見る
3. 目立って初めて、押し出し・分割とメッシュ統合に取り組む

理由: スキニングの学習（LBS・逆バインド行列・親子変換）はパーツ分離でも同じように学べる。
また、目立たなければ改造自体が不要になる。企画メモ13節「実際に痛かった箇所だけを実装する」。

### 2026-09-07 追記：判断を覆し、メッシュ統合（頂点編集）に進む

上記の「判断の順序」は3ステップ目（実際に痛くなってから着手する）を前提にしていたが、
Phase 5（ボーン+FK）とP8（曲面プリミティブ）を終えた時点で、**関節の割れを待つまでもなく
方針を変える理由が先に見つかった**。曲面プリミティブ（球・カプセル・円錐台）を組み合わせても、
目指す「滑らかなローポリキャラ」の輪郭には届かないと実物のプレビューを見て判断した。
プリミティブの組み合わせでは、パーツの継ぎ目に必ず段差や不要な内部面が残り、
分割数を増やしても輪郭線（トゥーン+アウトライン）が滑らかにならない。

そこで、「関節の割れが目立つかどうか」より前段の問題として、**造形そのものの限界**を理由に、
押し出し・頂点編集（メッシュ統合）へ進むことにした。以前の「先回りしてデータモデルを
作り替えない」という決定自体は誤りではなく、実際にプリミティブを組んで試すという手順を
飛ばさなかった結果として今の判断に至っている。つまり「試す前に作り替えない」の原則は維持しつつ、
試した結果として作り替えを決めた、という位置づけ。

**今回（土台）の範囲**: `mesh`型の追加、箱からの変換（`convertToMesh`）、描画（フラット法線・
3軸平面へのUV投影）まで。頂点・面そのものの編集（押し出し・辺の分割）は次の段階。
既存の5プリミティブ・5モードのギズモ・ペイント・ボーン・アニメ・MCP・JSON入出力は
そのまま残し、**プリミティブとメッシュの併存**（大まかな形はプリミティブ、
仕上げが必要なパーツだけメッシュへ変換）を狙う。

### 2026-09-07 追記：面選択・押し出し（頂点編集の第1段階）を実装

土台（mesh型・箱からの変換）に続き、押し出しを実装した。あわせて、土台段階のUV方式
（箱と同じ軸投影）では押し出しで斜めの面ができた際にテクセルが歪む問題を先に修正した
（詳細は`docs/開発ログ.md`参照）。

**実装した範囲**:
- UV方式を「面ごとの平面展開（面の辺を基準にした2Dローカル座標系）」へ変更。軸に平行な面
  （箱からの変換直後）では従来の6面展開と同じ領域サイズになることをNodeテストで固定した。
- 新モード「面 (F)」：メッシュパーツの面をクリックで選択（Shiftで複数選択）、半透明色でハイライト。
- 押し出し：選択面をツールバーの数値入力（1グリッド単位）で法線方向へ押し出す。元の面は新しい
  位置の面に置き換え、辺ごとに側面を追加する。1回の押し出し＝コマンド1回（`extrudeFace`）、
  距離0は発行しない。
- 押し出しで面構成が変わったメッシュのテクスチャは、面インデックスの対応関係から可能な範囲で
  引き継ぎ、新しくできた面は未指定（`.`）で埋める。
- MCPの`apply_commands`に`extrudeFace`を追加。

**次の段階（未着手だった）**: 頂点そのものの編集（ドラッグでの移動、辺の分割・マージ）。
押し出しは「面を複製して動かす」操作のため、頂点編集の基礎はここでほぼ揃った。

### 2026-09-07 追記：頂点編集（モード整理・頂点移動）を実装

面選択・押し出しに続き、頂点そのものの移動を実装した（辺の分割・マージは引き続き未着手）。

**モードの整理**: 専用モードを増やすとモードボタンが8個になり多すぎるため、Blenderと同じ
「メッシュ編集モードの中にサブモード（頂点／面）を持つ」構造へ整理した。「面 (F)」ボタンを
「メッシュ編集 (F)」に改称し、その中にサブ切替ボタン「頂点 (1)」「面 (2)」を追加した（数字キー
でも切替可）。面サブモードの機能（面の選択・押し出し）は一切変更していない。

**実装した範囲**:
- 頂点サブモード：mesh パーツの頂点を小さな球で表示する（`depthTest:false`＋高い`renderOrder`で
  常に手前、カメラ距離によらず画面上で一定サイズになるよう毎フレーム換算——面ハンドルと同じ手法）。
  クリックで選択（Shiftで複数選択）、何もない所をクリックで選択解除（パーツ選択自体は変えない）。
- 選択頂点群の重心へ移動ギズモ（TransformControls、`setTranslationSnap(1)`）を配置し、複数選択時は
  全頂点へ同じ量を加える。ワールド空間のドラッグ量をパーツの実際のワールド回転（ボーンの回転も
  含む）の逆回転でパーツローカルへ変換したうえで整数へ丸めるため、パーツやボーンが回転していても
  頂点座標は常に整数を保つ。
- `moveVertices`コマンドを追加（`{type:'moveVertices', partId, vertexIndices, delta}`）。ドラッグ中は
  プレビューのみ、離した時に1コマンドを発行する（既存の押し出し・リサイズと同じ作法）。移動量が
  `[0,0,0]`ならコマンドを発行しない。MCPの`apply_commands`にも追加した。
- 頂点移動で面の実寸（footprint）が変わるため、UVアトラスは押し出しと同じ`rebuildMeshTexture`
  （面インデックスは不変なので恒等対応）で作り直す。既存ピクセルは左上基準で可能な範囲を保持し、
  はみ出す分はステータスで「一部のテクスチャ内容が失われました」と通知する。
- `validateDoc`に、面積が0に退化した面（頂点の重なり・一直線上の並び）を検出する検査を追加した。
  実装判断としては**エラー**（例外を投げて適用を拒否）を選んだ。理由：警告として黙って通してしまうと、
  一度退化した面を含むdocは以降のあらゆるコマンド適用（`applyCommand`の末尾で毎回`validateDoc`が
  走る）で同じ検査に引っかかり続け、実質的に編集不能になる「地雷」になる。エラーにして
  「そのコマンド自体を拒否」する方が、既存の`execute()`のtry/catch経由でステータス表示され、
  ドキュメント自体は直前の有効な状態のまま保たれるため、事故が起きない。
- 非平面（4頂点が同一平面上に無い）四角形の扱いは、面ローカルのUV平面展開が最初の3頂点で平面を
  決める既存方式をそのまま使うことにした（詳細・制限は`docs/開発ログ.md`参照）。

**各機能への影響確認**: バウンディングボックス（`calculatePartBounds`→`meshBounds`が現在の頂点座標を
そのまま使うため自動追従）、ペイント（面のUVは現在の頂点から毎回再計算されるため頂点移動後の面にも
描画可能）、複製・左右ミラー（`duplicatePart`/`mirrorPart`は`vertices`を含めてパーツ全体を構造複製する
だけで頂点編集特有の分岐は無い）、ボーン割り当て・アニメーション（パーツ→ボーンの参照のみで頂点編集と
無関係）のいずれも、既存コードが型で分岐している箇所を確認し、追加のコード変更なしに正しく動作する
ことをNodeテストとブラウザ実機（人型サンプルの胴をmesh化し、頂点をドラッグ移動→UndoでJSON上のUV
サイズが元に戻ることまで確認）の両方で検証した。

**次の段階（未着手）**: 辺の分割・マージ、複数パーツの1つのmeshへの統合（メッシュ結合）。
