作成日: 2026-09-06

## このリポジトリの位置づけ

企画メモ 14 節「実装ステップ」の 1〜5 を、GitHub Pages で動くブラウザツールとして
段階的に実装する。いろはペイント／おとはピアノに続くシリーズ第3弾。

## 技術構成（プロトタイプ段階）

| 項目 | 選択 | 理由 |
|---|---|---|
| 実装 | 素の HTML + ES Modules（ビルド不要） | GitHub Pages に置くだけで動く。試行のサイクルが最短 |
| Three.js | CDN (jsdelivr) を importmap で読む | npm/Vite 導入は必要になってから |
| 言語 | JavaScript（TS は後回し） | プロトタイプ段階で型定義に時間を使わない |

> いろはペイントは Vite + TS だが、こちらは「動きを見ながら進める」段階なので
> あえてビルド無しから始める。規模が育ったら Vite へ移行する（src/ をモジュール分割しておく）。

## 最初から守る設計ルール（企画メモ 15 節）

MCP 対応を後から無料で足せるようにするため、以下 2 点はプロトタイプ第一版から守る。

1. **単一 JSON ドキュメントが唯一の真実**
   - `ModelDoc`（parts / bones / textures …）が状態のすべて
   - Three.js のシーンはそこからの派生物。逆方向に状態を持たない
   - パーツは安定 ID ＋ 意味のある名前（`arm_l` など）を持つ
   - 座標・寸法は整数グリッド単位
2. **すべての編集はコマンド経由**
   - `add_box` / `set_transform` / `delete_part` …
   - Undo/Redo はコマンド履歴で実現し、そのまま MCP の API になる

## 決めたこと・ペンディング

- 拡大は必ず整数倍。端数はレターボックス（黒帯）で埋める（企画メモ 3 節の絶対ルール）
- 1グリッドあたりの解像度は `doc.texelsPerUnit`（既定4）。箱は Minecraft / Blockbench 型の box UV、円柱は上下円＋側面帯へ自動展開する
- `doc.palette` は最大36色、テクスチャの `.` はパーツ色へフォールバックする。既存JSONは読込時に既定値を補い、textureなしの単色表示を維持する
- テクスチャは NearestFilter、mipmap 無効、SRGB。寸法変更時は左上基準で転写し、範囲外の着色ピクセル消失をステータス通知する
- ペイントはRaycasterのUVをアトラス座標へ変換し、同一パーツ・同一面内だけ直線補間する。1ストロークを`paintPixels`コマンド1件として確定する
- ボーンは親からの相対位置・回転を持つObject3D階層とし、パーツは1ボーンへ剛体割り当てする。パーツ座標は従来どおりモデル原点基準で、全ボーン回転0度をバインドポーズとする
- アニメーションはクリップ配列で保存し、現段階のUIは先頭クリップだけを扱う。フレーム移動の姿勢適用は履歴外、キー・fps・長さの編集はコマンド履歴へ積み、回転補間にはQuaternionのslerpを使う
- アウトラインは逆押し出しで開始。深度＋法線のエッジ検出は後で置き換え
- 公開先リポジトリ名は `tsumiki-modeler`（企画メモ 17 節）— まだ作成していない

## P8 曲面プリミティブ（完了）

- 円柱を`radiusTop`/`radiusBottom`対応へ拡張し、旧`radius`へのフォールバックを維持する。
- 球（radius/segments）とカプセル（radius/height/segments）を追加し、形状別プロパティ、面リサイズ、ペイント、自動UV、検証、MCPへ通す。
- 曲面はThree.js既定の共有頂点法線、箱は面ごとの法線を使い、既存3段階トゥーンを維持する。
- ティーポットを球の胴、円錐台の台座・蓋・注ぎ口、球のつまみ、カプセルの取っ手へ作り直す。

## メッシュ統合をいつ判断するか

現在はパーツを組み合わせる方式なので、接合部は**めり込んだまま**（内側の面が残る）。
不透明・トゥーン・384x216 では実害が無いが、**Phase 5 でボーンを入れて関節を曲げると、
接合部が割れて中身が見える**可能性がある。

一般的なキャラ制作は「1つの繋がったメッシュを押し出し・分割で成形する」方式で、
企画メモ12節も「メッシュは繋がっている方が、Blockbench 的なパーツ分離よりずっと良い」としている。

ただし**先回りしてデータモデルを作り替えない**。ModelDoc は今「パーツの配列」だが、
押し出しを入れると「頂点と面の配列」が必要になり、改造が大きい。

**判断の順序（決定）**
1. まず現状のパーツ分離のまま Phase 5（ボーン + 剛体スキニング）を通す
2. 実際に関節を曲げて、384x216 でどれだけ割れが目立つかを見る
3. 目立って初めて、押し出し・分割とメッシュ統合に取り組む

理由: スキニングの学習（LBS・逆バインド行列・親子変換）はパーツ分離でも同じように学べる。
また、目立たなければ改造自体が不要になる。企画メモ13節「実際に痛かった箇所だけを実装する」。
